# M0.4 — Windows guest boots to winload/kernel inside KVM

Status: ⬜ planned

## Goal

The headline milestone: VaultBoot's promise kept for real — the user's
**official, unmodified** Windows boot files (`bootmgfw.efi → winload.efi →
ntoskrnl`) execute as a KVM guest, driven by a host chain that is entirely
AcreetionOS-owned and that Windows Update can never overwrite or reset.

## Deliverables

1. Guest OVMF, in the M0.3 harness, reads the **user's own Windows ESP**
   read-only from pass-through and emits `Windows-Boot-Manager` serial.
2. Windows disk passthrough (full-disk, not just ESP — winload needs the
   BCD, the page handling path, and (per-entry) actual OS volumes):
   - per-entry, **opt-in** passthrough config — never a default,
   - BCD read (parse `\EFI\Microsoft\Boot\BCD` in the guest OVMF boot path
     normally, or with a pre-staged minimal BCD on the guest virtual ESP
     that points at read-only sector offsets — decide here and document
     the choice as the canonical one).
3. `initramfs/init` hardening: after guest handoff, host initramfs tears
   down to a hardcoded receipt exit; **no shell in the host boot chain**.
4. `test/test_ovmf_windows.sh` — e2e (testbed/booters): CI runs Windows
   boot inside docker-in-TCG unless a KVM-capable runner exists (mirror
   acreetboot 0.7-CI constraint note about us_ssh nested-virt limits).
   Marker: `Windows-Boot-Manager`.
5. Manifest verification for payloads the host launches (align with
   acreetboot manifest discipline; the guest's own SB validation is
   internal to the guest).

## Acceptance criteria

- [ ] `Windows-Boot-Manager` serial assertion green in committed harness.
- [ ] host chain truly R/O over Windows ESP; guest scratch-ESP only.
- [ ] No modification of Microsoft binaries anywhere; grep-guard remains.
- [ ] Receipts (build + test) committed for the marker.

## Dependencies

M0.3 (KVM host boots guest OVMF + virtual ESP).

## Out of scope

NVRAM guard (M0.5), user-installer CLI (M0.6).
