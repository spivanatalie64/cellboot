# M0.5 — NVRAM guard

Status: ⬜ planned

## Goal

Close the second half of the "Windows fights back" problem: even though
`\EFI\cellboot\` removes the file-overwrite vector, Windows feature updates
still reset UEFI NVRAM `BootOrder` / `BootNext` opportunistically. The
NVRAM **guard** refuses or restores any Windows-side reset attempt so the
AcreetionOS-owned chain is never silently demoted — and, as a consequence
of it working, the abandoned `\EFI\Microsoft\Boot\` entry doesn't even
need to be relied on.

## Deliverables

1. `c/nvram-guard.c` (and, if needed, an in-initramfs variant) — functions:
   - snapshot current `BootOrder`, `BootNext`, `BootCurrent` (+ cellboot
     entry markers under a cellboot-owned efi variable name, e.g.
     `ACREET-CELLBOOT-REF-XXXX`),
   - detect foreign rewrites (`BootOrder` losing the AcreetionOS entry);
   - **restore-first, refuse-second**: on detect, rewrite correct value;
     if rewrite fails (some firmware genuinely blocks), poweroff honestly
     with serial trace and a visible one-liner message before dying.
2. Wire-guard into all boot hops for M0.3/M0.4 harness runs so the guard
   runs every boot, not only "when someone remembers".
3. Spec doc for the guest side: contract reasons Windows might legitimately
   want to set `BootNext` (e.g. its own `efi changes`) — define the
   allow-list, default deny.
4. Tamper test:
   - `test/test_nvram_tamper.sh` — QEMU/OVMF boots, mid-boot a tiny helper
     (stub OS-side) rewrites `BootOrder` to drop the AcreetionOS entry;
     harness asserts the guard *restored* it and the marker is green.

## Acceptance criteria

- [ ] Tamper test green: `BootOrder` verified restored by the watchdog
      within a bounded number of firmware cycles; not by accident but by
      assertion.
- [ ] Guard is in the boot path of every committed harness (M0.2/3/4/5 run
      together in `test/run_all.sh`).
- [ ] Honest bail-out on firmware refusal (exit code recorded, no fake
      "protection succeeded").

## Dependencies

M0.3+ (needs the micro-init runtime in place to actually run the guard).

## Out of scope

Signing/MAC manifest sealing of the guard binary itself (acreetboot 0.5 lane;
mirror it here later, tracked but not this milestone's scope).
