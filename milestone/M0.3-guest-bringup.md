# M0.3 — Guest bring-up: KVM host boots guest OVMF from the user's Windows ESP

Status: 🔨 **in progress** (2026-10-15, branch `feature/cellboot`) — the
host initramfs init is REAL now (not the scaffold stub): `cellboot.esp=`
required cmdline contract, READ-ONLY Windows ESP mount verified back
through /proc/mounts (rw ⇒ unmount+poweroff, exit 121), KVM probe (exit
120), honest decline-to-guess. Remaining: guest scratch ESP staging, guest
OVMF boot + `CELLOVF-GUEST-START` marker, kill of the `init`-level
handoff-not-implemented stop (exit 119).

## Goal

Swap the M0.2 stub payload for the real Windows-guest launcher: a minimal
**KVM-capable Linux microkernel + initramfs** that CellBootLauncher.efi
starts, which then boots a *guest* OVMF reading the user's own Windows boot
files off their Windows ESP — passed through as a virtual disk.

This is the moment CellBoot stops being a payload launcher and becomes the
overwrite-immune KVM lane.

## Deliverables

1. `initramfs/` — busybox-style init:
   - mounts the Windows ESP **read-only** on the host (hard rule),
   - stages a guest scratch disk (tmpfs-backed, tiny) as the guest's *own*
     virtual ESP — the guest never touches the real ESP's writes,
   - records host-side KVM readiness (module loaded or honest bail-out).
2. Linux microkernel config (`initramfs/kernel-config` or equivalent):
   `CONFIG_KVM`, `CONFIG_KVM_INTEL`/`AMD` enabled, everything
   performance-irrelevant stripped; `lockdown=confidentiality` +
   `module.sig_enforce=1` cmdline baked into the build receipts.
3. `CellBootStub`-trajectory extension: CellBootLauncher now launches the
   kernel instead of a general PE32+ — adapt or keep stub for regression.
4. `test/test_ovmf_guest.sh` — QEMU/OVMF e2e:
   - host boots (real stage), loads KVM, spawns guest OVMF,
   - serial asserts **`CELLOVF-GUEST-START`** (proposed marker) once the
     guest OVMF banner appears,
   - guest disk = throwaway image with a debug payload, NOT a real
     Windows ESP yet (that is M0.4).
5. `c/` — first helper lands: guest device-path resolver (locates
   `\EFI\Microsoft\Boot\bootmgfw.efi` on the *read-only* real ESP to figure
   out the pass-through sector mapping; pure read, verified via manifest
   later).

## Acceptance criteria

- [ ] Harness green with `CELLOVF-GUEST-START` + M0.2's `CELL-PAYLOAD-OK`
      still asserted (regression-safe).
- [ ] Real Windows ESP is mounted RO — enforced in init, not just assumed;
      add an explicit init check that destroys boot if R/W was possible.
- [ ] Guest sees its own virtual ESP; no leaked host writes.
- [ ] tree lineage notes: Linux microkernel lane shared with, but separate
      from, acreetboot's miniboot (`efi/miniboot`) — no cross-vendor
      shortcuts.

## Dependencies

M0.2 (payload launch mechanism proven in KV-run firmware).

## Out of scope

Actual Windows booting (M0.4), NVRAM guard (M0.5).
